## M01 - Windows gcloud helper timeouts do not contain descendant processes

**Evidence:** [connection.py](../src/piccolo/providers/gcp/connection.py), `GCloudConnection.invoke`, lines 166–214, especially the narrow job-protected tunnel branch at lines 189–196 and ordinary `subprocess.run` at lines 197–208. Configuration inspection enters this path from `environment` at lines 131–133, and native SSH token acquisition and OS Login operations enter it through [ssh_auth.py](../src/piccolo/providers/gcp/ssh_auth.py), `KeyAuthorization.request` at line 100 and `oslogin` at lines 293–320. The already implemented protected alternative is [process.py](../src/piccolo/process.py), `managed_process` at lines 20–57 and `run_command` at lines 71–138, backed by [win32process.py](../src/piccolo/win32process.py), `process_job` at lines 25–67.

Ordinary native Windows gcloud calls still use `subprocess.run`; only the application-tunnel branch and prompted SSH/SCP capture use the job-protected runner. On Windows, CPython's timeout handler kills the root process and then drains captured stdout/stderr without another timeout. A surviving descendant retaining either pipe can keep that drain blocked, despite the requested operation deadline. The new native SSH preparation path depends on these ordinary gcloud calls before its protected SSH process can start. This is a Windows-specific containment gap in the helper path, rather than a failure of the existing OpenSSH job implementation. The [official CPython subprocess implementation](https://github.com/python/cpython/blob/main/Lib/subprocess.py) supports the observed root-kill/unbounded-drain behavior.

**Impact and Conditions:** If the selected SDK launcher or a helper it invokes spawns a descendant inheriting captured output handles, timeout or cancellation may leave that descendant running and delay the reported failure indefinitely. A connection or bootstrap receipt operation can remain blocked before SSH launches, and cooperative live-test deadlines cannot be treated as effective local process bounds for this branch. The audit demonstrated the condition using harmless Python sleepers, not an ordinary production SDK invocation that happened to spawn such a child. It does not establish credential disclosure, arbitrary command injection, an unauthenticated remote exploit, or cancellation of an already accepted cloud request. Severity is Medium because the defect defeats an explicit availability/cleanup guarantee under the stated condition.

**Reproduction:** On native Windows, construct a `GCloudConnection` from the local example configuration, replace only its launcher with a harmless Python shim, and call `invoke` directly with a one-second timeout and `use_flags=False`. The shim starts a three-second child inheriting stdout/stderr, prints a marker, and sleeps for ten seconds. No real gcloud command or credential is used. The root was killed at timeout, but Piccolo returned its one-second timeout error only after **3.301 seconds**, when the descendant released the pipes. Passing the identical shim through `run_command(..., timeout=1)` returned after **1.059 seconds**, demonstrating the effectiveness of the existing Windows job boundary. The sleepers exited or were job-terminated; no intentional test child was left running.

```python
import os
import sys
import time
from pathlib import Path

from piccolo.config import load
from piccolo.errors import PiccoloError
from piccolo.providers.gcp.connection import GCloudConnection

connection = GCloudConnection(load(Path("examples/gcp/piccolo.toml")).gcp)
shim = (
    "import subprocess,sys,time; "
    "subprocess.Popen([sys.executable,'-c','import time; time.sleep(3)']); "
    "print('audit-child-started',flush=True); time.sleep(10)"
)
connection.launcher = lambda: [sys.executable, "-c", shim]
started = time.monotonic()
try:
    connection.invoke(
        ["config", "list"], os.environ.copy(), timeout=1, use_flags=False
    )
except PiccoloError as error:
    print(round(time.monotonic() - started, 3), error)
finally:
    connection.host_directory.cleanup()
```

**Recommendation:** Route all native Windows gcloud invocations through the existing job-protected process runner, retaining inspected environments, explicit identity flags, `use_flags`, capture/foreground behavior, and the remaining operation deadline. Include configuration inspection, account listing, token acquisition, and OS Login commands rather than only tunnels. Add a separately selectable native Windows regression at the `GCloudConnection.invoke` boundary that launches an inheriting descendant, checks timely return, and verifies descendant termination on timeout and cancellation. Keep POSIX transport behavior and the generic versus Windows-specific test boundary intact. No implementation or regression-test remediation was made during this audit.
