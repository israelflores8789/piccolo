## Assessment

Piccolo implements several valuable safeguards, especially explicit bootstrap authorization, durable mutation intent, conservative treatment of uncertain Compute operations, stop-before-snapshot relocation, and attachment checks before disk deletion. Nevertheless, the audit found reproducible recovery and environment-selection defects, incomplete enforcement of connection identity, and important conditional risks for research data and credentials. Resolve the High findings affecting Piccolo before relying on unattended relocation or cleanup of valuable environments.

No Critical vulnerability or actual compromise was established. Six findings are ranked High, twelve Medium, and two Low. High findings include operational failures with significant availability or data-recovery consequences, as well as conditional security risks.

The locked third-party dependency set contains 68 packages. Both PyPI and OSV audits reported no known vulnerabilities for those exact versions, including the two Windows-only entries. However, `pytest>=8.0` permits versions affected by CVE-2025-71176; the locked and tested version, 9.1.1, is unaffected. A clean locked-version scan does not establish that every version permitted by the package metadata is safe.

## Scope, assumptions, and limitations

Reviewed the application under `src/piccolo/`, configuration schema and examples, `pyproject.toml`, `uv.lock`, `justfile`, pre-commit configuration, README, lifecycle/bootstrap/SDK/connection/state tests, live fixtures and independent janitor. Reviewed the agreed design doc, the agreed live test design doc, and the canonical scripts for local startup, infrastructure management, and example bootstrap in their entirety. The final accepted decisions in the agreed design doc take precedence over earlier superseded proposals: SDK provisioning, explicit bootstrap, staging without execution, three distinct identity responsibilities, and preservation of research data.

The supplied design documents and canonical scripts were untracked at audit start. They were treated as evidence and preserved. The threat model includes an accidental configuration collision, interruption or loss of local state, concurrent cloud administration, inherited workstation authentication settings, untrusted credential configuration, and compromise of a guest or project-owned bootstrap dependency. Several findings require those conditions; they are not unauthenticated remote exploits against the CLI.

All executable checks were local and cloud-free except public package/advisory/documentation lookups. No GCP authentication refresh, project inspection, infrastructure mutation, SSH session, tunnel, secret access, live test, canonical script execution, publishing, release, or push was performed. The local `gcloud version` command was informational only. Actual organization policies, IAM grants, firewall hierarchy, guest hooks, image package vulnerabilities, container configuration, credentials, Windows behavior, and cloud cost were not inspected. The external repository/container build referenced by the bootstrap is outside this workspace. Git history was not exhaustively scanned for secrets.

Severity reflects consequences for this research-environment use case. **Confirmed** means reproduced locally or directly established from source; **Conditional** identifies a source-supported risk requiring the stated circumstances; **Reference** applies to a canonical script, not automatic Piccolo runtime behavior. These are audit priorities, not CVSS scores unless an advisory score is explicitly supplied.

### H01 — Inherited credentials can override the reported gcloud identity — RESOLVED

**Evidence:** [connection.py](src/piccolo/providers/gcp/connection.py), `run` at line 59, `flags` at line 35, and `check_identity` at line 82; [gcp_live.py](tests/gcp_live_support/gcp_live.py), preflight at line 263; [test_gcp_live.py](tests/test_gcp_live.py), environment checks at line 73.

The subprocess environment removes only `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE`. It retains `CLOUDSDK_AUTH_ACCESS_TOKEN`, `CLOUDSDK_AUTH_ACCESS_TOKEN_FILE`, and `CLOUDSDK_AUTH_IMPERSONATE_SERVICE_ACCOUNT`. Persisted gcloud properties such as `auth/access_token_file` and `auth/credential_file_override` are also unexamined. Passing `--account` and reading `gcloud auth list` do not establish the effective principal when higher-priority credentials are present. A local mocked subprocess probe confirmed that all three environment overrides survive an explicit configured account. Google's documented credential precedence establishes why this can change the principal. [Google Cloud CLI authentication](https://docs.cloud.google.com/sdk/docs/authenticate).

**Impact and conditions:** A workstation with inherited token or impersonation settings can connect, transfer bootstrap, or open IAP under a different principal than Piccolo reports. Explicit project selection remains in place, but authorization attribution and the intended provisioner/connector boundary can be wrong. Live fixtures reject those three environment variables and configured impersonation, but do not reject the two persisted token/credential-file properties. The live tunnel test also calls `subprocess.Popen` directly at line 299 without a sanitized environment, allowing `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE` to reach that tunnel even though ordinary `GCloudConnection.run` removes it.

**Recommendation:** Establish a complete connection credential policy. Reject conflicting environment and persisted authentication overrides before connection work, or use a deliberately isolated CLI configuration with an explicitly selected method. Report both source and impersonated target where applicable. Validate that policy on every SSH/SCP/status-receipt path, including `bootstrap --status`, which can call `execute` without `ready` or `check_identity`. Add checks for persisted properties, not just environment variables.

#### Remediation

Every gcloud transport command now rejects inherited access-token, token-file, credential-file, impersonation, and credential-disabling overrides and inspects the active configuration for persisted authentication overrides. The connection selects and binds its login account, reports the source account and configured impersonation target, and enforces the same policy for SSH, SCP, IAP, and bootstrap receipt reads that bypass readiness. The live tunnel subprocess receives an environment checked by the shared policy, and live preflight checks connection identity before constructing SDK clients.

**Regression Coverage:** [test_connection.py](../tests/test_connection.py) checks inherited overrides across SSH, SCP, and IAP command construction; persisted token-file, credential-file, impersonation, and credential-disabling properties; account selection for receipt reads without readiness; and overrides introduced after identity was checked. Assertions ensure rejection happens before transport and does not print override values. [test_gcp_live.py](../tests/test_gcp_live.py) adds gated real gcloud property-parsing cases in a disposable configuration directory and rejection before guest command, transfer, or tunnel access. Local coverage passed; live cases remain unexecuted.

### H02 — Externally supplied credential JSON is not validated — RESOLVED

**Evidence:** [auth.py](src/piccolo/providers/gcp/auth.py), `credentials` at line 17; [loader.py](src/piccolo/config/loader.py), credential-file handling at line 119.

The loader verifies that a credential file exists, then calls the generic `google.auth.load_credentials_from_file` without validating credential type, endpoints, credential-source URLs/files, or trust provenance. ADC may also obtain externally configured credentials. Google explicitly warns that accepting unvalidated credential configuration from an external source can compromise systems and data, and the current upstream generic loader is deprecated in favor of more deliberate handling. [Google authentication user guide](https://github.com/googleapis/google-auth-library-python/blob/main/docs/user-guide.rst), [upstream credential loader](https://github.com/googleapis/google-auth-library-python/blob/main/google/auth/_default.py).

**Impact and conditions:** If an operator accepts a credential JSON from an untrusted repository or third party, malicious external-account configuration can redirect credential acquisition or token exchange and expose credentials or local/network data. Executable credential sources additionally depend on the authentication library's executable opt-in; arbitrary execution is not assumed enabled by default. Even a read-oriented command such as `plan` constructs SDK credentials. No malicious credential refresh was executed during this audit.

**Recommendation:** Define supported credential types and their provenance; validate externally sourced configuration before invoking generic loaders or SDK clients. Prefer operator-controlled ADC or keyless impersonation/federation. Treat TOML, credential JSON, readiness commands, executable discovery, and bootstrap as trusted executable configuration, and explain that `validate` checks schema/files rather than credential safety. Type-specific loaders should still receive vetted inputs.

#### Remediation

SDK credential JSON is read once, validated, and passed to a type-specific service-account or authorized-user loader instead of a generic credential loader. Supported files must use the Google OAuth token endpoint and the `googleapis.com` universe; external-account, GDCH, embedded impersonation, and credential-source or alternate-endpoint configurations are rejected. The same policy covers configured files, `GOOGLE_APPLICATION_CREDENTIALS`, and the well-known gcloud ADC file. Without a local ADC file, authentication uses Google metadata credentials; provisioner impersonation remains explicit in TOML. The README and configuration schema document supported types, operator trust requirements, and the distinction between local TOML validation and SDK credential validation.

**Regression Coverage:** [test_auth.py](../tests/test_auth.py) checks rejection before library loading for URL, file, and executable external sources; unsupported credential types; alternate token endpoints and universes; and embedded impersonation across all three file-discovery paths. It also covers malformed JSON, missing fields/files, valid user ADC without token refresh, type-specific service-account loading, metadata credentials, and explicit impersonation. [test_gcp_live.py](../tests/test_gcp_live.py) adds gated rejection before SDK construction for invalid configured-file and ADC inputs; its existing human-source case exercises genuine provisioner impersonation. Local coverage passed; live cases remain unexecuted, and deliberately invalid credentials are never refreshed by the rejection cases.

### H03 — Resume cannot recover a later fallback candidate — RESOLVED

**Evidence:** [provider.py](src/piccolo/providers/gcp/provider.py), `choose` at line 267 and `resume` at line 569. Existing tests independently cover fallback and first-candidate lost responses, but do not combine those conditions.

`choose` starts from the first configured candidate on every resume. Before replaying that candidate's recorded terminal failure, it rejects any same-name VM outside the source/current candidate zones. If a previous run exhausted the first zone and then successfully submitted a VM in a later zone, an interruption or lost response leaves that later VM visible. Resume rejects it before reconciling its recorded request.

**Reproduction:** Using the existing FakeCloud, make `instance.insert` in `us-west1-a` return terminal capacity exhaustion, then accept creation in `us-east1-b` and lose its response. A new provider's `resume` raises `Another same-name VM exists; no additional creation is safe` without additional submissions. The same sequence during a move, with `us-east1-b` exhausted and `us-east1-c` accepted, fails identically and leaves the source stopped. Both cases were reproduced locally.

**Impact:** A central design guarantee fails during precisely the capacity-fallback workflow the utility is intended to support. Recovery remains blocked, daily commands remain blocked by the journal, and a move may leave two billable resources with the source stopped. Existing protections prevent blind duplication, which is good, but do not provide a usable recovery path.

**Recommendation:** Reconcile recorded candidates and accepted operations before rejecting an expected later candidate. Persist the chosen candidate/attempt state and distinguish its VM by immutable identity and operation ownership. Cover fallback combined with interruption at submission, polling, staging/readiness, and commit.

#### Remediation

Candidate selection now skips positively recorded terminal capacity failures before checking topology for the next candidate, while still blocking fallback if a failed zone contains a VM. The journal persists the candidate zone and exact observed resource identities. Resume reconciles the accepted candidate using the original request and operation records, checks ownership and recorded identities, and retains the existing protections against uncertain submissions and duplicate creation.

**Regression Coverage:** [test_security_lifecycle.py](../tests/test_security_lifecycle.py) combines first-candidate exhaustion with later acceptance and interruptions during init submission, polling, or staging and move submission, polling, readiness, or durable commit. Tests assert the same replacement ID survives recovery, no creation is resubmitted, only one VM remains, and the journal resolves. [test_gcp_live.py](../tests/test_gcp_live.py) adds the same gated interruption matrix around genuine SDK submission, operation recovery, SSH, staging, and relocation with an injected capacity failure. Move fallback requires three approved zones and reports a skip with fewer; init fallback requires two. Local coverage passed; live cases remain unexecuted.

### H04 — Cleanup trusts absence of a local operation as proof of safety — RESOLVED

**Evidence:** [provider.py](src/piccolo/providers/gcp/provider.py), `cleanup` at line 628 and `continue_cleanup` at line 666; [journal.py](src/piccolo/state/journal.py), `state_directory` at line 17 and missing-state initialization at line 35.

When no local unresolved operation is present, cleanup makes every owned disk/snapshot with a nonempty operation label eligible, except attached disks. It does not require a known completed operation, check journal-history references, or establish whether a cloud operation remains unresolved elsewhere. A new `PICCOLO_STATE_DIR`, deleted journal, different workstation, or another user's home directory produces an empty operation while matching cloud labels remain.

**Reproduction:** Leave a move unresolved after an accepted destination creation, keep its original journal, then create a provider with the same configuration and a fresh state directory. Its cleanup preview lists the move snapshot as eligible; `cleanup(True)` deletes that snapshot while the original journal still records an unresolved move. This was reproduced with the existing cloud fake. Attachments protected both boot disks in this example, but did not protect the snapshot.

**Impact:** Recovery evidence and copies needed to reconstruct a failed environment can be irreversibly removed. Missing local knowledge becomes deletion authority. Labels alone are ownership hints, not evidence that recovery has finished. The documented single-workstation convention does not protect against state loss or an accidental state-directory change on that workstation.

**Recommendation:** Require a positively recorded resolved operation and exact resource manifest for automated cleanup, retain unknown-operation artifacts, and independently check cloud operations and environment topology. Make state loss an explicit recovery/adoption mode with conservative deletion rules. Keep a recoverable state backup or cloud-side operation manifest; coordinate mutations if multiple state roots can exist.

#### Remediation

Generic cleanup now requires a positively completed init/move history entry containing an exact artifact manifest, matching environment/operation labels and immutable resource IDs, settled cloud operation results, and one unambiguous recorded active VM. It independently checks disk attachment references and rechecks this authorization before each deletion, including resumed cleanup. Missing state, unknown operations, old history without manifests, changed identities, unresolved requests, or unavailable operation evidence retain recovery artifacts for manual inspection; absence of a local operation no longer grants deletion authority.

**Regression Coverage:** [test_security_lifecycle.py](../tests/test_security_lifecycle.py) verifies that both a fresh state root and a deleted journal preserve an unresolved move snapshot during cleanup preview and apply. Additional cases remove manifests, history, active identity, terminal operation evidence, or safe topology, replace a resource ID, and remove history after cleanup intent is journaled; none authorize deletion. Existing lifecycle tests still exercise cleanup after a resolved rollback and protection of foreign or attached disks. [test_gcp_live.py](../tests/test_gcp_live.py) adds gated preservation of a real unresolved move snapshot under a fresh state root, followed by recovery through the original journal. Local coverage passed; live cases remain unexecuted.

### H05 — Environment ownership is not checked when selecting an existing VM — RESOLVED

**Evidence:** [provider.py](src/piccolo/providers/gcp/provider.py), `instances` at line 73, `active` at line 81, `init` at line 159, and `move` at line 393; [lock.py](src/piccolo/state/lock.py), line 15.

Selection uses project and VM name, then checks an immutable ID only if one is already recorded locally. A fresh environment journal does not reject a VM positively labeled as belonging to another Piccolo environment. Existing `init` can likewise reconcile access after its managed-settings comparison. Locks are keyed by environment, so two configurations naming the same VM but using different environment names have independent locks.

**Reproduction:** Provision `test-env`, then construct a configuration with `environment='another-env'` and the same project/name. Its `stop` succeeds against the first environment's VM, without an adoption step or ownership mismatch. This was reproduced locally. The same selection path feeds relocation, which can delete the selected source VM after commit.

**Impact and conditions:** An accidental configuration collision can stop or relocate another environment and alter access resources, even on one workstation. The operator must already possess the relevant GCP permissions; this is a failure of Piccolo's environment boundary, not an IAM authorization bypass.

**Recommendation:** Reject positively foreign ownership before any lifecycle/access mutation. Provide deliberate adoption for an unlabeled legacy VM, record its immutable ID, and distinguish that from selecting another Piccolo environment. Lock conflicting resource identities as well as configuration/environment identity. Document that metadata/key publication by connection commands may also mutate guest access.

#### Remediation

VM selection and lifecycle/access continuations now reject positively foreign or incomplete Piccolo ownership, including when a local instance ID matches or `init --adopt` is supplied. Unrecorded legacy VMs require explicit adoption, which records the immutable instance ID before access reconciliation and grants no bootstrap freshness. Ownership is rechecked during resumed init, power operations, source inspection, replacement commitment, and committed cleanup. Local mutation locks now cover both environment identity and project/VM name within one state root. The new adoption CLI regression also exposed and prompted correction of noninteractive spinner handling so mutating commands reach the provider.

**Regression Coverage:** [test_security_lifecycle.py](../tests/test_security_lifecycle.py) checks foreign-environment rejection for init, adoption, start, stop, move, and bootstrap status without cloud or access mutations; deliberate legacy adoption and subsequent ID replacement; foreign ownership during resumed init; and replacement ownership changed during readiness. [test_config.py](../tests/test_config.py) exercises the actual `init --adopt` CLI path, and [test_state.py](../tests/test_state.py) verifies that different environments selecting the same VM share a resource lock. [test_gcp_live.py](../tests/test_gcp_live.py) adds gated cross-environment init/adoption, stop, and move rejection against real run-owned resources. Local coverage passed; live cases remain unexecuted.

### H06 — Shutdown scripts bypass the automatic lifecycle-script guard — RESOLVED

**Evidence:** [provision.py](src/piccolo/providers/gcp/provision.py), `reject_startup` at line 57 and source validation at line 69; [provider.py](src/piccolo/providers/gcp/provider.py), `stop` at line 358 and move's stop-before-snapshot sequence at line 464.

The metadata guard rejects startup-script, sysprep, and user-data keys, but accepts `shutdown-script` and `shutdown-script-url`. Both accepted keys were confirmed with direct local calls. Project metadata uses the same incomplete guard, and ordinary `stop` does not perform lifecycle metadata checks. Google shutdown scripts can execute as root when a Linux VM stops or is deleted. [Google shutdown-script documentation](https://docs.cloud.google.com/compute/docs/shutdownscript), [official guest-agent implementation](https://github.com/GoogleCloudPlatform/guest-agent/blob/main/google_metadata_script_runner/main.go).

**Impact and conditions:** An adopted VM or project with destructive shutdown metadata can run that code during `move` before Piccolo snapshots the disk, or during a daily `stop`. Source metadata also preserves these hooks onto the replacement. This can erase or alter research data without invoking the explicit bootstrap command. Actual destructive guest execution was not performed.

**Recommendation:** Inspect known automatic shutdown/startup mechanisms at all supported metadata scopes before lifecycle mutations; reject or require deliberately reviewed policy for those hooks. Extend the live preflight and tests. Inspection of guest services/cron/cloud-init remains a separate requirement and cannot be inferred from metadata alone.

#### Remediation

The automatic metadata guard now rejects shutdown-script keys and URLs, including prefixed variants, alongside startup scripts, sysprep, and user-data. Instance and inherited project metadata are checked before lifecycle/access mutations. Ordinary stop, resumed power operations, and retired-source deletion now enforce the guard, including shutdown metadata added after replacement readiness or durable commitment. Live preflight uses the expanded guard. Guest services, cron jobs, and arbitrary image-installed hooks remain outside this metadata policy.

**Regression Coverage:** [test_security_lifecycle.py](../tests/test_security_lifecycle.py) covers shutdown-script, shutdown-script-url, and a Windows-prefixed shutdown key at both instance and project scopes across init, start, stop, and move, asserting no mutations. It also checks resumed stop and late project metadata that blocks source deletion after commitment. [test_gcp_live.py](../tests/test_gcp_live.py) adds gated harmless instance shutdown-hook writes, verifies stop/move rejection, restores original metadata, and tests inherited project hooks through a read overlay. Offline live-harness coverage verifies that metadata writes are bound to an exact run-owned ID, journaled with a request UUID, and submitted without retries. Local coverage passed; live cases remain unexecuted.

### M01 — IAP configuration does not establish an IAP-only network — RESOLVED

**Evidence:** [loader.py](src/piccolo/config/loader.py), `external_ip=True` at line 173 and CIDR parsing at line 186; [access.py](src/piccolo/providers/gcp/access.py), firewall creation/comparison at line 237; the canonical example bootstrap script, `podman run -p 8080:8080` at line 85.

Fresh VMs have a public IP by default, including the ordinary example. Configured source ranges need only be valid IPv4 CIDRs, so `0.0.0.0/0` is accepted. The firewall checks its own named rule, not other VPC/hierarchical rules or effective guest ingress. Its service-account target covers all VMs using that account, making a dedicated account important. The canonical container publishes port 8080 on host interfaces; application authentication was not inspectable here.

**Risk:** Existing broad ingress rules can expose SSH or the development service directly, bypassing the intended IAP entry point. A correctly scoped Piccolo rule does not restrict another allow rule. `via_iap=false` also cannot use an external address when none exists, and the transport offers no explicit internal-IP mode for that case.

**Recommendation:** Prefer private VMs for the supported IAP workflow, flag broad ranges/public ingress in `plan`, inspect effective firewall policy, and document intentional public/internal connection modes. Treat code-server/container authentication as an independent requirement. Validate guest egress prerequisites when choosing a private VM; IAP ingress does not supply internet access for package installation.

#### Remediation

New VMs and the tracked examples now default to no external IP. IAP source CIDRs must be contained in `35.235.240.0/20`; broad and unrelated ranges are rejected at configuration load. Planning reports effective VPC/inherited ingress and the private-guest egress prerequisite. Provisioning rejects allow rules that could expose the configured ports outside IAP, and SSH/SCP target checks re-read effective instance ingress. These checks conservatively reject potentially applicable rules rather than claiming complete deny/allow priority analysis. Intentional direct public or private transport is explicit through `external_ip`, `via_iap`, and `internal_ip`; public addresses and ports outside the configured set remain operator responsibilities. Cloud NAT or another egress route, application authentication, and guest firewall inspection remain external prerequisites.

**Regression Coverage:** [test_security_medium.py](../tests/test_security_medium.py) covers private defaults, rejected IPv4/IPv6 source ranges, explicit internal transport, and broad VPC/hierarchical ingress rejected before access writes. [test_sdk.py](../tests/test_sdk.py) verifies private VM creation payloads. Live effective-policy and egress validation remain unexecuted.


### M02 — IAM privilege and identity separation need stronger checks — RESOLVED

**Evidence:** [loader.py](src/piccolo/config/loader.py), project-role validation at line 204; [access.py](src/piccolo/providers/gcp/access.py), unconditional additive grants at line 19; [provision.py](src/piccolo/providers/gcp/provision.py), VM cloud-platform scope at line 210.

`project_roles` accepts syntactically valid broad roles, including Owner/Editor, and creates unconditional grants even where only a conditional grant already exists. This is consistent with the additive configuration contract but materially widens privilege. Runtime provisioning does not enforce that the guest account differs from the provisioner or inspect the guest's existing effective roles. The live helper's separation check is stronger than the runtime path. Any code able to use the VM's metadata credentials can act with the guest account's permitted authority; rootless containers alone do not establish a cloud identity boundary.

**Recommendation:** Show dangerous roles and conversion from conditional-only to unconditional access prominently in planning; support a least-privilege policy. Keep provisioner/connector/guest responsibilities distinct, avoid attaching the provisioner to the VM, scope secret grants individually, prefer keyless credentials, and inspect inherited IAM. Cloud-platform scope is appropriate only alongside restrictive IAM. The default empty project-role list is a useful control.

#### Remediation

Configured guest project roles and individually scoped secret grants remain additive and apply only to the service account in TOML. Basic, administrative, and credential-delegation guest roles are rejected, and custom definitions are inspected for privileged permissions. Planning inspects direct project/folder/organization grants to the guest; known privileged grants block provisioning. Group membership and condition evaluation still require operator review. The provisioner cannot be attached as the guest account: supported file/impersonation credentials are checked without refresh at load, and metadata-derived identity is checked after ordinary SDK reads. Conditional-only grants for the same guest member and role cannot be widened automatically, and IAM writes require an etag. SDK permission failures, including terminal Compute authorization errors, identify the provider-qualified role, acting identity when available, and binding resource. User ADC without an exposed email is identified honestly as the configured ADC/file provisioner; the guest account is never substituted as the acting identity.

**Regression Coverage:** [test_security_medium.py](../tests/test_security_medium.py) checks provisioner/guest separation for direct, impersonated and metadata-derived identities, dangerous guest roles and custom token/administrative permissions, inherited guest privilege reporting, conditional-only rejection, missing etags, durable guest-only IAM additions, and action permission guidance naming the provisioner rather than the guest. [test_sdk.py](../tests/test_sdk.py) retains etag-conflict and unrelated-condition preservation coverage. [test_auth.py](../tests/test_auth.py) verifies credential loading without refresh. Live IAM inheritance and identity behavior remain unexecuted.


### M03 — SSH authentication policy depends on implicit gcloud defaults — RESOLVED

**Evidence:** [connection.py](src/piccolo/providers/gcp/connection.py), SSH/SCP arguments at lines 119 and 190 and global `--quiet` at line 37; [provision.py](src/piccolo/providers/gcp/provision.py), fresh VM metadata construction at line 195.

Piccolo does not explicitly select OS Login, block project metadata SSH keys, expire published keys, or establish verified host-key enrollment. gcloud's documented default accepts a host key on first connection and checks it on subsequent connections; `--quiet` can generate the default SSH private key without a passphrase. These are documented defaults, not proof of a successful interception. IAP lowers network exposure but does not validate an SSH host key by itself. [gcloud SSH reference](https://docs.cloud.google.com/sdk/gcloud/reference/compute/ssh).

**Recommendation:** Define supported OS Login/metadata-key policies, report effective mode, bind the configured POSIX user to the actual connector, and establish a host-key trust procedure for new and relocated instances. Specify SSH key lifetime/protection. Test key publication and OS Login separately because an authenticated SSH probe may itself publish keys or change access state.

#### Remediation

Piccolo follows the accepted policy: gcloud owns SSH authentication key creation, storage, and publication; Piccolo does not inspect, replace, repair, or certify existing authentication keys or store passphrases. OS Login versus metadata-key access remains GCP/user policy. Host public keys are fetched from the guest agent through authenticated Compute guest attributes, enrolled only after checking the selected immutable instance/disk identity, and used with strict checking for SSH and SCP. New VMs enable guest attributes; readiness waits for host-key publication without accepting an unknown key. Relocated/existing guests require a working agent and effective guest-attribute publication. A private temporary gcloud home gives its default known-hosts path the authenticated enrolled keys, while the original gcloud config and normal user authentication-key path remain explicit. Inherited SSH config, global host files, host-key commands, DNS trust, and automatic host-key updates are disabled. Automated commands check the actual POSIX login user. `gcp.ssh.expire-after` defaults to `24h` and requests finite published access for both SSH and SCP; it does not terminate established sessions or delete private keys. `gcp.ssh.require_passphrase` defaults to false; true omits `--quiet`, uses terminal prompt forwarding, and rejects disabled prompts or missing terminals. Existing encrypted keys may need the SSH agent because automation uses batch mode. Verified transport currently supports Linux/macOS OpenSSH and rejects Windows SSH/SCP. Trusted GCP administrators, the guest image/user, and the workstation remain part of the host-trust boundary.

**Regression Coverage:** [test_security_medium.py](../tests/test_security_medium.py) covers authenticated enrollment and API permission distinctions, unknown/replaced-instance rejection, host-publication polling, isolated gcloud home and retained authentication-key/config paths, SCP strict checking/expiration/batch flags, actual prompt forwarding with framed command output, a bounded interactive subprocess deadline with inherited descendant stdout, and immediate POSIX-user mismatch rejection. [test_connection.py](../tests/test_connection.py) retains credential-override and transport/readiness checks with host enrollment injected. [test_gcp_live.py](../tests/test_gcp_live.py) now adds eight gated expiration/reconnection cases covering SSH/SCP, OS Login/instance metadata, and both guest-account variants. Disposable keys are used on fresh VMs without bootstrap staging; direct OpenSSH must first reject an actually expired key without republishing it. Piccolo/gcloud must then renew the same public key with a later expiration, and SCP must preserve probe bytes. [test_ssh_expiry.py](../tests/test_ssh_expiry.py) covers the observation/renewal sequence, timeout and network-failure distinctions, same-key assertions, raw-probe isolation, and cleanup proof checks. The existing offline live-safety suite checks janitor recovery and mode selection before first access. Disposable profile/private-key cleanup is journaled and available to the independent janitor. Real expiration/reconnection, encrypted-key prompts, guest-agent enrollment, and Windows behavior remain unexecuted.

### M06 — Access mutations are only journaled as a broad reconciliation stage — RESOLVED

**Evidence:** [provider.py](src/piccolo/providers/gcp/provider.py), `access` at line 203; [access.py](src/piccolo/providers/gcp/access.py), API/account/grant/firewall mutations at lines 144–281.

The operation journal records the access stage, but not each IAM addition, service-account creation, API enablement, or firewall request/result. A later failure can leave unconditional grants or infrastructure in place without a complete manifest. Runtime firewall creation lacks a persisted request UUID/operation identifier; a timeout is reconciled by future GET. IAM etags and additive retries limit lost updates, but do not solve partial-operation accounting. Ordinary `cleanup` retains accounts, rules, APIs, and IAM grants by design.

**Recommendation:** Record each intended/completed access mutation, immutable identity where available, and whether the resource or grant preexisted. Expose partial results and an explicit, conservative recovery/removal policy. Reinspect pending operations before treating a missing firewall as permission to create again. Require an etag when writing IAM, as the live helper already does, and keep unrelated grants/conditions intact.

#### Remediation

Access reconciliation now records separate durable `access_actions` for API enablement, service-account creation, IAM additions, and firewall creation. Each action records intent, preexistence, observed identity, request UUID, returned operation ID where available, and outcome; operation IDs are flushed before waiting, including across keyboard interruption. Status exposes partial results. Resume observes current resources and reconciles pending firewall operations by saved operation/request ID before proceeding; missing or uncertain account/API results are retained for manual inspection rather than blindly resubmitted. IAM merges preserve conditions/unrelated grants and require etags. IAM/account/API services do not all support request UUIDs, so a journal UUID does not imply server idempotency. Cleanup retains access resources and grants. Recovery/removal policy is explicitly manual and conservative: verify current identity, scope, preexistence, sharing, and pending outcomes before externally removing anything.

**Regression Coverage:** [test_security_medium.py](../tests/test_security_medium.py) checks persisted IAM intent/completion, configured-guest-only grants, missing-etag/conditional rejection, firewall request UUIDs and lost-response reconciliation without a second insert, saved firewall operations before waits and after interruption, and API intent/operation persistence and uncertain outcomes without re-enablement. [test_sdk.py](../tests/test_sdk.py) exercises etag retries, and the offline [live harness](../tests/test_gcp_live_safety.py) remains passing with its enclosing manifest intents. Real access reconciliation remains unexecuted.


### M07 — Creation and relocation do not fully bind observed resource identity/settings — RESOLVED

**Evidence:** [provider.py](src/piccolo/providers/gcp/provider.py), `created` at line 210, fresh-disk recording at line 318, and snapshot cleanup at line 557; [provision.py](src/piccolo/providers/gcp/provision.py), source denylist at line 77 and reconstruction at line 171; [resources.py](src/piccolo/providers/gcp/resources.py), mutation requests at line 147.

Creation verification checks labels and READY/RUNNING, but does not persist and enforce the Compute operation's immutable `target_id` against every later observation. Fresh bootstrap eligibility is assigned from the disk observed attached after creation rather than an independently recorded fresh-disk identity. Snapshot cleanup checks operation labels but no previously recorded snapshot ID. Source validation rejects selected unsupported fields while reconstruction preserves a selected subset; an unrecognized/default-changing SDK field or separately attached cloud policy can be silently lost. Read-then-mutate requests still target names and have a concurrency window.

**Risk and conditions:** Another cloud administrator, a second state root, or a replaced resource carrying matching labels can alter what is adopted, snapshotted, or deleted. No malicious cloud race was executed. Some protections are already strong: source/replacement VM IDs and source-disk IDs are checked, and generic cleanup rechecks recorded IDs and attachments.

**Recommendation:** Persist IDs from successful create operations and verify exact attachment/source relationships before assigning bootstrap freshness or deleting recovery objects. Define explicit supported settings/defaults and inspect related policy/tag bindings instead of relying on a selective denylist. Document residual races and enforce coordination for destructive work.

#### Remediation

Compute create actions persist terminal operation `target_id`, and created resources must match that ID, ownership, readiness, and requested settings. Fresh/replacement disk IDs are recorded independently of VM observations, verified against exact attachment/user relationships, and rechecked before bootstrap staging or execution. Snapshot source disk IDs and restored disk source snapshot IDs must match the recorded recovery chain; snapshot deletion also requires the recorded snapshot ID. Relocation uses explicit supported-field sets, rejects unknown nondefault VM/disk/nested settings, preserves supported disk descriptions/architecture/labels, and inspects separately attached source instance/disk tag bindings before source mutations. Known resource policies and other unsupported settings remain rejected. GCP requests still mutate by name, so a race with another administrator or state root cannot be eliminated; destructive work requires external coordination, and failed identity/settings checks retain recovery state.

**Regression Coverage:** [test_security_medium.py](../tests/test_security_medium.py) checks replaced Compute target IDs, independently replaced boot-disk identities, requested creation settings, disk swaps during readiness with no upload, replaced snapshot IDs retained during cleanup, unsupported source settings before stop, and zonal instance tag-binding inspection. Existing lifecycle/fallback/cleanup regressions remain passing. Real cloud races, related-policy inheritance, and tag-binding API behavior remain unexecuted.


### M08 — Staging paths are syntactically safe but not confined or uniformly private — RESOLVED

**Evidence:** [loader.py](src/piccolo/config/loader.py), remote-path checks at line 228; [staging.py](src/piccolo/bootstrap/staging.py), directory creation and upload at lines 55–77; [execution.py](src/piccolo/bootstrap/execution.py), runner upload at line 111.

Rejecting absolute paths, traversal, and shell metacharacters is useful. However, a safe relative path can resolve through a preexisting symlink outside the home directory. Parent directories are created with ambient permissions, and the upload exists before its later `chmod 600`. The runner is uploaded without an explicit post-upload chmod or digest check, though the execution directory/log uses `umask 077`. Existing files and same-user modifications are trusted.

**Risk and conditions:** On a shared or previously configured guest, a script containing sensitive configuration may be exposed during transfer, redirected, or replaced between digest validation and execution. An actor already able to modify the development user's home is a substantial existing compromise; this finding does not assert a new privilege escalation over that user.

**Recommendation:** Establish private parent/upload/runner permissions before transfer, reject unexpected symlinks/ownership, reserve Piccolo receipt paths, verify the runner, and validate the artifact at launch. Keep secrets out of staged scripts and explicitly state the guest-user trust boundary.

#### Remediation

Remote parents are checked for symlinks and ownership and secured to 0700 before transfer. Upload and runner files are precreated as owned regular files with one hard link and mode 0600; private local byte snapshots request the same permissions from SCP, removing the earlier transfer exposure window. Reserved receipt/upload/runner names cannot be configured as scripts. Script and runner digests are verified, ownership/path checks repeat at launch, and execution uses the same open file descriptors that were hashed. The provider rechecks instance/disk identity around staging and before authorization. This Linux guest path requires `stat`, `id`, and `/proc/self/fd`; scripts using `BASH_SOURCE` now see the verified descriptor path and should use explicit paths or `$HOME` for resources. Same-user or guest-kernel compromise remains inside the trusted execution boundary, and sensitive secrets should not be embedded in staged scripts.

**Regression Coverage:** [test_security_medium.py](../tests/test_security_medium.py) checks symlinks at each staging level with no copies/outside writes, pre-transfer 0700/0600 permissions including local snapshots and runner files, reserved/noncanonical paths, runner digest tampering with no launch, and disk replacement during readiness. [test_bootstrap.py](../tests/test_bootstrap.py) retains real local guest execution, failure receipts, and one-attempt protections. Real guest transfer/ACL behavior remains unexecuted.


### M09 — Timeout and power-state commands can leave bootstrap partially applied

**Evidence:** [execution.py](src/piccolo/bootstrap/execution.py), detached launch at line 120 and wait deadline at line 138; [provider.py](src/piccolo/providers/gcp/provider.py), `move` bootstrap-state guard at line 396 and unguarded `stop` at line 358.

The bootstrap timeout bounds polling; it does not kill the detached script. A timed-out script can keep mutating the guest indefinitely. Receipt loss remains uncertain and correctly blocks another attempt, but there is no supported cancellation/completion-repair workflow. `move` blocks started/uncertain bootstrap, while `stop` can interrupt it without that guard. A failed or partially applied bootstrap has no automatic recovery, which is safer than replay but operationally consequential.

**Recommendation:** Document the timeout as an observation deadline, expose the remote process/receipt and deliberate cancellation procedure, and apply consistent guards before stopping a guest with an unresolved attempt. Maintain the no-automatic-retry rule. Review configured readiness commands too: they are opaque code executed repeatedly by connection readiness and must be nondestructive.

### M10 — Diagnostic output and state directories need a confidentiality boundary

**Evidence:** [provider.py](src/piccolo/providers/gcp/provider.py), full instance/operation output at line 112; [cli.py](src/piccolo/cli.py), JSON rendering at line 54; [journal.py](src/piccolo/state/journal.py), directory and atomic-file handling at line 68; [manifest.py](tests/gcp_live_support/manifest.py), saved records; [gcp_live.py](tests/gcp_live_support/gcp_live.py), baseline inventory at line 277.

Status and operation history can contain complete instance metadata and source descriptions. Live manifests also retain full baseline inventories. If a preexisting VM's custom metadata contains sensitive values, these can reach console logs/state; configured bootstrap output can contain anything the opaque script prints. New state files use private mkstemp permissions and new environment directories request 0700, but an existing directory's ownership/mode/symlinks are not validated or repaired. Windows ACL behavior was not exercised.

**Recommendation:** Redact/classify metadata before emitting it, document that bootstrap logs inherit script sensitivity, validate existing state storage ownership/permissions, and protect retained live artifacts. Configure Git exclusions or secret detection for operator credential JSON; the supplied `.gitignore` protects live run directories and dotenv but is not a comprehensive credentials policy. No credential-file contents or real secret payloads were collected during this audit.

### M11 — Relocation has no post-commit recovery retention or data validation

**Evidence:** [provider.py](src/piccolo/providers/gcp/provider.py), readiness/commit at line 493 and immediate resource cleanup at line 519; [test_gcp_live.py](tests/test_gcp_live.py), sentinel verification occurs after `move` returns at line 253.

Authenticated SSH confirms guest access, not preservation of every research workload or writable container layer. After readiness, Piccolo immediately deletes its owned source disk and the recovery snapshot. A migrated VM can boot and answer SSH while an application is corrupt or data is incomplete. The test's sentinel hashes are useful evidence for a future live run, but are checked after runtime cleanup and do not provide a general production integrity check. Stop-before-snapshot improves consistency; it does not establish application consistency under every guest shutdown condition.

**Recommendation:** Provide a configurable retention/explicit-finalization policy for valuable environments, inspect workload-specific health/integrity before destroying recovery copies, and maintain independent backups. Keep automatic readiness nondestructive and require more than a generic `true` probe when workload integrity matters. Clarify downtime, address changes, single-disk support, and that rollback after replacement commitment is currently unsupported.

### M12 — Live-test gates are useful but do not implement the entire approval contract

**Evidence:** The agreed live test design doc; [gcp_live.py](tests/gcp_live_support/gcp_live.py), `profile` at line 25 and `preflight` at line 160; [test_gcp_live.py](tests/test_gcp_live.py), existing secret handling at lines 99 and 155; [manifest.py](tests/gcp_live_support/manifest.py), independent cleanup at line 203.

Arbitrary configured existing secret IDs are accepted as approved targets. Their payload is later retrieved and compared to a dummy hash, after the temporary guest-account access grant; a mistakenly selected real secret has already been exposed to that guest principal at that point. Use an isolated project and dummy secrets as planned.

**Recommendation:** Bind the run to a reviewed approval manifest, enforce explicit duration/resource budgets, validate allowed dummy-secret identities before IAM writes, reject all credential overrides, and arrange independent cleanup before execution. Include ordinary runtime paths in the authorized validation matrix and record skipped variants, failed stages, costs, and zero-leftover inventory.

## Controls verified

These controls describe the original audited revision; remediation additions are documented in the respective finding sections.

- Config discovery is current-directory-only; explicit missing paths do not fall back; unknown keys/types and conflicting option positions fail locally.
- SDK clients share one resolved provisioner credential object, use the explicit configured project, and do not generate service-account keys.
- Local transport uses argument arrays and `shell=False`; the Windows branch avoids `.cmd`/`.bat` shell interpolation through a Python entry point. That branch has mocked coverage, not a real Windows execution result.
- IAP tunnels bind to loopback; readiness uses an authenticated SSH probe and bounded retries.
- IAM merges request policy version three, preserve unrelated bindings/conditions, retain etags, and reread on conflicts. Missing configured grants are intentionally unconditional.
- Compute mutation request UUIDs are persisted before submission; automatic mutation transport retries are disabled. Only structured terminal capacity errors trigger another zone.
- NotFound is distinguished from permission/transport failure; incomplete aggregated discovery warnings are rejected.
- Move stops before snapshotting, preserves a single persistent boot disk's content through a snapshot, checks source/replacement IDs, and requires SSH before durable commitment.
- Extra disks, local SSDs, selected unsupported encryption/network/scheduling settings, and known startup metadata are rejected rather than intentionally migrated.
- Bootstrap is explicit, verifies local/remote script digests and fresh-disk eligibility, records attempt authorization before launch, claims a guest receipt directory atomically, and blocks repeat/changed/failed/uncertain attempts. No force/replay bypass was found.
- State files use atomic replacement, file/directory fsync on supported POSIX paths, and private temporary files. Kernel locks block a separate local process and release on exit.
- Cleanup previews by default and rechecks ownership, recorded immutable IDs, and disk attachments before deletion, subject to H04's incomplete eligibility rule.
- Live tests are skipped without pytest opt-in; mutations additionally require explicit environment opt-in and exact approved project. Janitor and fixture manifests are durable and teardown preserves unowned resources and unrelated IAM conditions/members.

## Reproduction and evidence

The baseline `uv.lock` SHA-256 is `30da757ce9e8905f8b53336a85059d2bce66805e5848f4749f1507d80f904edb`; `pyproject.toml` SHA-256 is `3f5c14f9bcaae77b053c2d691de9e491c7972ba5072469922bb2d4b0ba76b2d6`. Findings and dependency results refer to that snapshot plus the supplied untracked references.

Audit commands can be repeated without changing dependencies. Exporting with `--frozen` and omitting the project avoids resolving upgrades or submitting Piccolo itself as a third-party package:

```bash
just ci
uv export --frozen --all-extras --all-groups --no-emit-project --format requirements-txt --output-file /tmp/piccolo-security-requirements.txt
uv run --with pip-audit --no-project pip-audit --no-deps --disable-pip --strict -r /tmp/piccolo-security-requirements.txt --format json --output /tmp/piccolo-security-pypi-audit.json --progress-spinner off
uv run --with pip-audit --no-project pip-audit --no-deps --disable-pip --strict -r /tmp/piccolo-security-requirements.txt --vulnerability-service osv --format json --output /tmp/piccolo-security-osv-audit.json --progress-spinner off
uv run --with bandit --no-project bandit -r src/piccolo tests/gcp_live_support -f json -o /tmp/piccolo-security-bandit.json
```

All-platform audit inputs were generated from every versioned third-party entry in `uv.lock`, removing environment markers and excluding the local Piccolo package. Minimum-version inputs pinned each declared `>=` floor exactly. The temporary files include `/tmp/piccolo-security-all-lock.txt`, `/tmp/piccolo-security-all-lock-audit.json`, `/tmp/piccolo-security-all-lock-osv.json`, `/tmp/piccolo-security-minimums.txt`, `/tmp/piccolo-security-minimum-audit.json`, `/tmp/piccolo-security-registry-check.json`, and `/tmp/piccolo-security-repro.py`. They are session evidence, not durable repository artifacts; the essential versions/results/reproduction conditions are included in this report. The minimum audit's exit code 1 reflects the pytest advisory; Bandit's exit code 1 reflects its two reviewed Low notices, not failed parsing.

- Review the external container/repository and effective network/IAM boundaries before using the canonical example bootstrap script.
- Raise the pytest security floor and establish ongoing scans for locked, downstream, build, external-tool, and guest/container dependencies.
- Add targeted regression coverage for the reproduced combinations, then perform the separately authorized disposable-project validation with bounded scope and independent cleanup. Complete real Windows/Python 3.12 checks and post-move integrity evidence before relying on those support claims.
